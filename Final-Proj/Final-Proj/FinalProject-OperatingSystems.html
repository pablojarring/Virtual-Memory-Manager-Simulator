Overview

The ultimate objective is to implement a simulation of a Virtual Memory Management system. Only a single process is considered(i.e., there is one address space) and only its memory accesses are considered(no simulation of the process’ execution).

A Java package called vmsimulation is provided to you. This package contains all basic simulation functionalities that you’ll use, and you cannot modify it. It has the following 5 classes all documented in this javadoc:

  • BitwiseToolbox: a small class with two static methods that are used to manipulate binary data.
  • MemoryException: a tiny exception class for our (simulated) system.
  • MainMemory: an abstraction of the main memory.
  • BackingStore: an abstraction of the backing store (i.e., the disk).
  • Simulator: the simulator itself, which uses dynamic class loading to test your code. It implements a main method that takes several command-line argument. The first one is the version of implementation : “V0” (Problem #0), “V1” (Problem #1), “V2” (Problem #2), “V3” (Problem #3), or “V4” (Problem #4).

In each of the subsequent questions, you must implement a class called VirtualMemoryManagerVx (for x=0, 1, 2, 3, 4). For each you are given a java source file with method declarations, and you must “just add code”. Each VirtualMemoryManagerVx must all be declared to be part of the vmmanager package

Note that some of the methods will be unchanged between versions, and you can thus “cut-and-paste” some code from one version to the next. (In real life, cut-and-pasting code is evil, but we’re doing it here because we’re doing incremental development so that you can get some credit even if you don’t finish the assignment entirely!)

There are 3 methods you should implement in the VirtualMemoryManagerV0 class:

  • writeByte(): a method that is given a 4-byte integer (the physical address), and a byte (the value), and writes in RAM (i.e., the simulated MainMemory) the value at the address; and also prints to System.out some helpful message.
  • readByte(): a method that is given a 4-byte integer (the physical address), and returns the value in RAM (i.e., the simulated MainMemory) at that address; and also prints to System.out some helpful message.
  • printMemoryContent(): a method that prints out to System.out the content of RAM.

Important: The physical address is passed to writeByte and readByte as a 4-byte integer, i.e., a 32-bit address. However, we’ll simulate RAM way smaller than 232 bytes! If we simulate a RAM with 2n bytes, then you will have to “extract” the low n bits from the 32-bit integer. For instance, if the simulated RAM is supposed to be 32 bytes, and the 4-byte integer given to you as an address is 1110 1111 1100 1101 0010 1011 0111 0101, then you would actually use 10101 as a 5-bit address (which as an int in decimal would then be 21, which you would then pass to MainMemory for reading/writing).

Such bit-wise operations are easily done with the useful methods provided by the BitwiseToolbox class (see the javadoc).

Problem #1: Virtual Address Translation with a Page Table

In this and all following questions we now simulate a disk (or “Backing Store”), and assume that the process address space fills up the whole disk. We simulate demand paging (i.e., the use of a page table and of page faults to cause pages to be loaded from disk into RAM). In this question we assume that the RAM size is equal to the disk size. This means that we’ll never need to evict any page back to disk because the entire address space fits in RAM. The simulator initially fills the disk with random data, which is the content of the process address space.

The main objective here is to perform address translation from virtual to physical, using the following steps as explained at length in the lecture notes:

  • Based on the virtual address determine the virtual page number and the offset;
  • Look up the page table to see if the page is loaded in a frame;
  • If it isn’t, then load it in a frame and update the page table;
  • Translate the virtual page number into a physical frame number and construct the physical address;
  • Access the data in RAM at that physical address.

Important: You’re on your own for implementing a page table, and you can use whatever data structure you want. It’s likely a good idea to have a class called PageTable (perhaps nested inside your VirtualMemoryManagerV1 class, with some lookup() and update() methods and whatever other methods your need).

All the above is to be implemented in a class called VirtualMemoryManagerV1, filling in all the empty methods in this VirtualMemoryManagerV1.java file that you should use a a starting point. This is the only file you need to modify.

More specifically, you’ll to implement the following methods:

  • writeByte(): same purpose (but different implementation) as in the previous question
  • readByte(): same purpose (but different implementation) as in the previous question
  • printMemoryContent(): same purpose (and same implementation!) as in the previous question
  • printDiskContent(): a method that prints out the bytes stored on the disk
  • writeBackAllPagesToDisk(): a method that writes back all pages that are in RAM to disk
  • getPageFaultCount(): a method that returns the number of page faults that have occured up to now
  • getTransferedByteCount(): a method that returns the number of bytes that have been transferred between RAM and disk up to now

Implementing these methods will require that you add new instance variables to the class (e.g., a page fault counter, a page table) and of course you’re allowed to add code to the constructor.

Problem #2: FIFO Page Replacement

We now enhance things further, in class VirtualMemoryManagerV2, so that we can handle an address space that’s larger than RAM space. Essentially, what your code must do is:

  • Keeps a list of free frames;
  • Evicts a victim page whenever a new page must be brought in and there are insufficient free frames;
  • Always selects the victim as the page that was brought into memory the longest time ago (your page table entries could keep track of some notion of time, or you could keep a FIFO data structure of page numbers that is separate from the page table);
  • Always write a victim page back to disk.
